## 1. Purpose

Create, from the skill, the NPS and Facilitators surveys that the Upcoming reports as
missing, with a preview of the exact plan, explicit approval, a re-check right before
writing, sequential execution that stops on the first error, a read-back, and the Slack
page refreshed with the new links and QR codes. This is increment V2-2 of
`documentation/V2_CLAUDE_NATIVE_ARCHITECTURE.md` (§6.2).

## 2. Context

- V2-1 (read-only Upcoming) is functional; its parallel run against desktop v1.0.2 runs in
  parallel with this work. **No real write happens before the first V2-1 parallel runs are
  clean** (see §9).
- Today every SELAM survey is created by a person in the Salesforce UI through a screen
  flow (`Survey_Set_Bulk_Generation` / `SF_NPS_Survey`). Screen flows cannot be launched
  through the connector, so V2 must reproduce what they write.
- Connector tools available: `salesforce_query`, `salesforce_describe`, `salesforce_create`,
  `salesforce_update` (and `salesforce_delete`, which V2 never uses).

## 3. Verified creation recipe (read-only discovery, 2026-11-26)

Checked on **all 48 survey sets** of the week 24–30 Nov 2026 (AR, BR, Nexo, MX; created by
five different people) and on the related invitations and projects. Real ids stay out of the
repository except the org-level constants below.

Per survey to create (one kind for one project):

1. **Create `SurveyInvitation`**
   - `Name` = `"<Survey.Name> for <Project.Name>"`, cut to 255 characters (44/48 match; the
     4 differences are projects renamed after the survey was created).
   - `SurveyId` = the country's survey (registry).
   - `CommunityId` = `0DB390000004Cy1GAE` (the "act" site; 48/48).
   - `OptionsAllowGuestUserResponse` = `true`,
     `OptionsAllowParticipantAccessTheirResponse` = `false`,
     `OptionsCollectAnonymousResponse` = `false` (48/48).
   - Owner = creator (48/48): no `OwnerId` is sent.
2. **Read back** the invitation: `Id` (18 characters) and `InvitationLink` (generated by
   Salesforce, with the 15-character id).
3. **Derive the link and QR** (48/48):
   - `link` = `InvitationLink` with `invitationId=<15-char id>` replaced by the 18-char id,
     plus `&guestUserLang=<language>`;
   - `QR_Code_URL__c` = `link` URL-encoded with no safe characters
     (Python `urllib.parse.quote(link, safe="")`).
4. **Create `Survey_Set__c`**: `Project__c`, `Survey__c`, `Survey_Language__c` (country
   language), `SurveyNPS__c` (`true` for NPS, `false` for Facilitators), `IpAddress_Restricted__c`
   = `false` (48/48), `Survey_Invitation__c`, `Survey_Invitation_Link__c` = `link`,
   `QR_Code_URL__c`.
   - Known automation: the after-save flow `create_Survey_Subject` runs on Survey Set
     (expected; verified in the pilot). No Apex triggers on either object.
5. **NPS only — update the project**: `rosscrooke__Project__c.Survey_Invitation__c` = the
   NPS invitation id (27/27 projects with an NPS set point to it; none without).

Unknowns the pilot must settle (§8): whether the screen flow writes anything else (project
fields, sharing, survey subject), the `CreatedBy` identity of connector writes, and whether
any e-mail is sent.

## 4. Scope

In scope:

- Plan from an Upcoming run: one command per missing survey kind of each **pending,
  eligible** session (the same rules as V2-1; excluded, review and out-of-scope sessions are
  never planned). Special cases are created as usual and flagged for the personalised e-mail.
- Preview page (UI kit, D-V2-11): sessions, survey, language, what will be written; the
  user can remove sessions; the plan hash is shown.
- Approval in the chat of **that hash**; re-check; sequential execution; read-back;
  reconcile; refreshed Slack page; creation log (Excel).

Out of scope: posting to Slack (V2-3), e-mails (V2-5), deleting or editing existing surveys,
fixing data-quality findings, any project field other than `Survey_Invitation__c`.

## 5. Flow and commands

The engine stays deterministic; Claude only runs what it prints, exactly as in V2-1.

1. `upcoming` (V2-1, unchanged).
2. **Preflight (identity and permissions):** before planning writes, `describe` of
   `SurveyInvitation`, `Survey_Set__c` and `rosscrooke__Project__c` as the connector's user
   must show the needed fields as createable/updateable; otherwise the run stops with a
   clear message. The operator is never hard-coded: it is whoever runs the session
   (D-V2-4), and it is read back from `CreatedBy` of the first record written.
3. `plan --run DIR [--exclude PROJECT_ID ...]` → `plan.json` (commands with an idempotency
   key `project:kind`), `plan.html` (preview), `plan_hash` (SHA-256 of the canonical plan).
4. The user approves in the chat by confirming the hash. Without that exact hash, `execute`
   refuses to start.
5. `recheck --run DIR --approve HASH` → re-check queries; drops commands whose survey now
   exists; if anything changed, a new plan and hash are shown and approval is asked again.
6. `execute --run DIR` prints **one** write at a time (`salesforce_create` /
   `salesforce_update` with exact JSON). After each call, `record` saves the response (from
   the session log, like `capture`) and validates it; the next write depends on it (the
   invitation link feeds the survey set). Any unexpected response stops the run.
7. `reconcile --run DIR` → read-back queries; per command: created / skipped / failed /
   partial (for example an invitation without its survey set). Never deletes anything;
   partial items are reported with links for a manual fix.
8. Outputs, delivered to the user as files at the end of every creation run (D-V2-2):
   - the **refreshed Slack page** with the new links and QR codes — the operational record,
     ready to paste;
   - the **creation log** `creation_log.xlsx`: a "Surveys" sheet with one row per planned
     survey (date and time, operator, country, client, session, survey, language, status
     created / skipped / failed / partial, invitation id, survey set id, link, Salesforce
     links) and a "Run" sheet (run id, selection, approved plan hash, operator, start and
     end, counts, errors). Written with the standard library (no extra dependency);
   - `result.html` (UI kit) and `audit.json` in the run folder (same content, for Claude).
   The durable trace is Salesforce itself (`CreatedBy`, `CreatedDate` on every record);
   `reconcile` can rebuild the log from it if a session is lost.

## 6. Safety rules (additions to architecture §7)

| Risk | Control |
|---|---|
| Duplicate survey | per-kind state + re-check right before writing + idempotency key; `execute` checks the key against a fresh read before every create |
| Writing the wrong thing | payloads built only by code from the recipe in §3; Claude never edits them; tests per country and kind |
| Half-done creation | sequential writes, stop on first error, reconcile reports partial items; no automatic delete |
| Approving one thing, executing another | hash of the canonical plan; `execute` refuses any other plan |
| Missing permissions or a different operator | preflight `describe` as the connector's user; the operator recorded from `CreatedBy`, never assumed |
| Unattended writes | never: the scheduled Monday run stays read-only; creation always needs a person's approval in the chat |
| Real data in the repository | fixtures are synthetic; the creation log is delivered to the user, never stored in the repository (D-V2-2) |

## 7. Implementation steps (each with tests, delivered as Codex packages)

1. **Recipe builders** (`nps_v2/creation/recipe.py`): invitation payload, link and QR
   derivation, survey-set payload, project update. Tests with synthetic values that mirror
   the 48/48 rules (15→18 id, `guestUserLang`, encoding, name cut at 255).
2. **Plan model** (`nps_v2/creation/plan.py`): commands from a report, exclusions,
   canonical JSON, hash. Tests: determinism, exclusions, nothing planned for non-pending
   sessions.
3. **`plan` command + preview page** (UI kit). Tests: page content, fallback rule, no real
   data.
4. **`recheck`**: re-check queries (reuse V2-1 readers), plan filtering, hash change.
5. **`execute` / `record`** step machine with the transcript capture and response
   validation; stop rules. Tests with simulated connector responses, including failures at
   every step.
6. **`reconcile`**, refreshed Slack page, `result.html`, `audit.json`.
7. **Creation log** `creation_log.xlsx` (standard-library writer; tests open it and check
   every column and the "Run" sheet).
8. **`SKILL.md`**: a "Create surveys" section with the non-negotiable rules (approval of the
   hash, one write at a time, stop on error, never delete).
9. **Pilot** (§8), then **rollout** (§9).

## 8. Pilot protocol (one project, PO present)

1. Pick one eligible pending project with both kinds missing, chosen by the PO.
2. Record the project's fields before.
3. Run plan → approve → execute for that project only.
4. Verify: invitation and set fields against §3 and against a set created by the UI the
   same week; `CreatedBy`; the survey subject exists; the project's `Survey_Invitation__c`;
   no other project field changed; the link opens the survey in the right language; the
   QR scans; no e-mail was sent (PO checks the inbox and the facilitators).
5. If anything differs from the UI, stop and decide: adjust the recipe, or path B.

## 9. Rollout and exit criteria

- Real writes start after: PO approval of this plan, at least
  the first V2-1 parallel runs clean, and the pilot passed.
- Then: a week with few sessions, the PO reviewing every result; then normal weeks.
- Exit: 2 consecutive weeks created by V2 with 0 manual corrections and reconcile all
  "created"; PO sign-off in §11.
